# App

## Formatting is Pint's job
Never hand-format PHP or Blade. `composer lint` applies the `pint.json` ruleset, `composer test:lint`
checks it. Both PHP and Blade go through Pint; Blade formatting is delegated to Prettier via Pint,
so there is no separate Prettier step and no `.prettierrc`.

## `declare(strict_types=1)` and `final` are enforced
Every file declares strict types and every named class is `final`. Both are Pint rules — do not add
`declare` or drop `final` by hand, and do not add a file missing them.

## Generated icon enums are exempt
`app/Icons/**` is generated by the NativePHP icon generator and is excluded from Pint. Never edit it
and never add logic to it.

## Prefer constructor/method injection over `app()`
Type-hint dependencies on component action methods. Only reach for `app(X::class)` where injection
isn't reachable. Existing debt: `PinkaryApi` is currently resolved via `app()` in many components —
prefer passing it in when touching those call sites rather than adding new ones.

## No custom Events/Listeners
Decouple side effects with `$this->async(...)` and its `->finished()`/`->failed()` callbacks. There is
no cross-component event bus in a NativePHP client; each screen is its own process.

## Use helpers over facades
Prefer `config()`/`auth()` helpers over the `Config::`/`Auth::` facades. Facades are the exception.

## Named routes only
Generate links with `route()` against a named route. Never build URLs by hand or concatenate the
API host — read it from `config('services.pinkary.url')`.

## Prefer static `Str::` helpers
Use `Str::limit`, `Str::startsWith`, `Str::contains` rather than `Str::of()` chains or bare `str_*`.

## No new top-level `app/` directories
The client has no `Actions`, `Controllers`, `Policies`, `Queries`, `Jobs` or `Notifications` layer and
should not grow one without a stated reason. Writes go through `app/Services`, and permissions are the
server's decision surfaced as a response code.

## No comments restating code
If a method or test name states the behaviour, do not add a comment above it. Comment only what the
code cannot say — the reason behind a non-obvious choice, or a workaround for a framework limitation.
